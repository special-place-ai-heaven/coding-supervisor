# Codex CLI T3 results: enforcement investigation

Date: 2026-10-29. Harness: `codex --version` = `codex-cli 0.165.0`. Status: harness side observed and receipted; live-model chair behaviour **not observed** (the ChatGPT account behind Codex hit its usage limit; see "Blocked"). Every claim below is tied to this version and this date.

## Adapter mode this evidence supports (one line)

**Enforcing on three named paths, advisory/audit everywhere else, with the chair played by a scripted model:** enforcing at (1) `PreToolUse` denial of nested local tool calls (`Bash` and `apply_patch` denied and not executed; `spawn_agent` reaches `PreToolUse` but its denial was not tried), (2) `Stop` refusal of a completion claim (the reason becomes a new user prompt; **no harness continuation cap** observed through 10 consecutive blocks, so the adapter must bound itself with `stop_hook_active` and its own count), and (3) `SubagentStop` refusal of a worker's handback (same mechanism); advisory/audit at the worker-result delivery (`PostToolUse` on the wait tool can annotate or replace the result inside the code cell, but the worker's verdict also reaches the chair as a `<subagent_notification>` message that fires no hook), at the outer code-mode `exec` cell (no hook fires for it), at tool calls the sandbox rejects (no `PostToolUse`), at hosted tools (documented, not tested), and at the acceptance moment (no event). Applies only when the project `.codex/` layer is trusted and the hooks are trusted (or `--dangerously-bypass-hook-trust` is passed).

## Setup

The repository ignores `.codex/` (root `.gitignore`) and `.agents/` (`.git/info/exclude`); the fixture's own `.gitignore` re-includes both.

- `--ignore-user-config` kept the user's `~/.codex/config.toml` (13 MCP servers, a `notify` program, user hooks in `~/.codex/hooks.json`, project trust entries) out of every run. Side effect: project trust and the `multi_agent` feature had to be given per run with `-c` and `--enable`.
- **Scripted model.** After the five live attempts failed at the usage limit, the chair and workers were played by `scripted-model/mock_model.py`, a local stand-in for the Responses API on `127.0.0.1:28431`, attached per run with `-c model_providers`. Whether a real model obeys the delivered reasons is **not** claimed.
- Codex 0.165.0 presents tools in **code mode**: the model gets one custom tool `exec` (JavaScript) plus `wait` and `request_user_input`; shell, patch and subagent tools are nested calls on a `tools` object (`tools.exec_command`, `tools.apply_patch`, `tools.multi_agent_v1__spawn_agent`, `tools.multi_agent_v1__wait_agent`, plus close, resume and send). ## Limits

- Chair and worker behaviour is scripted; a real model's response to `<hook_prompt>` reasons, annotations and denials is unverified on Codex.
- The worker result reaches the chair through `<subagent_notification>` without any hook, so a gate cannot hide or rewrite an unsupported verdict before the chair reads it; it can only annotate, refuse the chair's `Stop`, or keep the worker going at `SubagentStop`.
- The nested `Bash` `PostToolUse` carries no exit code; an adapter must parse output, use another path for it, or require the exit code in the worker's citation and accept "observed, exit unknown".
- No hook for the code-mode `exec` cell; JavaScript-only work is invisible, and the tool names seen by hooks are normalised (`spawn_agent`, `multi_agent_v1wait_agent`), not the names the model calls.
- `transcript_path` and `agent_transcript_path` were `null` in every run (`--ephemeral`); their non-ephemeral values are not recorded.
- Hosted tools (web search) skip tool hooks per the docs; not tested. `PermissionRequest` never fired (approval policy `never`).
- One port collision: from about 11:09 to 11:12 local, a sibling investigation's local stand-in (process serving `grok-4.6` requests) shared `127.0.0.1:18765` with this one. My runs from that window were discarded and the stand-in moved to 28431 with an exclusive bind; the sibling's requests in that window may have been answered by this stand-in.
