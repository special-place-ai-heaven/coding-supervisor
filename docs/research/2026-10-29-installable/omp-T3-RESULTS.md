# OMP T3 results: enforcement investigation for oh-my-pi

Date: 2026-10-29. Harness: `omp --version` = `omp/18.13.3`. Status: investigation complete in print mode (`omp -p`) only; no adapter built, no core change. Hook behaviour is version-dependent; every claim below is tied to this version, this date and this machine's user configuration.

## Adapter mode this evidence supports (one line)

**Enforcing on three named paths, advisory/audit everywhere else:** enforcing at (1) `tool_call` refusal of a tool call (`{block: true, reason}`; a handler that throws also refuses the call), (2) `before_subagent_spawn` refusal of a worker dispatch, and (3) `session_stop` refusal of a main-session completion claim (`{decision: "block", reason}`; ten consecutive refusals were all honoured, so no cap at 8 applies to explicit refusals; it is bounded only by the hook releasing, an operator interrupt, `--max-time` or `--max-cost`); advisory/audit at worker result delivery (`tool_result` on `task` or `wait`: annotation or content replacement, and the replacement is bypassable because the chair can read the original via `read agent://<id>`), at final-message rewriting (`assistant_message`), at worker handback (no stop event fires in subagent sessions), and at the acceptance moment itself, for which no event exists. An OMP adapter is an in-process TypeScript/JavaScript extension loaded by OMP, not a shell hook.

## Setup

- Fixture: `fixtures/omp-enforcement/` with a project hook module `.omp/hooks/pre/capture.ts`, a per-test policy `hooks/policy.json` (selected by the `OMP_T3_TEST` environment variable, because OMP assigns session ids itself and has no `--session-id` flag), two project agents `.omp/agents/fake-worker.md` (`tools: []`, replies `VERDICT: PASS` / `CHECKS RUN: 0`) and `.omp/agents/cited-worker.md` (`tools: bash`, `blocking: true`, runs `echo check-ok` and cites `CHECK C2 | echo check-ok | exit 0`), two marker skills `.omp/skills/omp-marker/SKILL.md` and `.agents/skills/agents-marker/SKILL.md`, `candidate.txt`, `gate-state.json` holding `{"state": "verifying"}` for every run, and a settings overlay `omp-config.yml` that turns off auto-learn, memory, advisor and prewalk so the runs write no learned skills or memories into the user's OMP home.
- The hook registers `pi.on(...)` for `session_start`, `session_shutdown`, `input`, `before_agent_start`, `agent_start`, `agent_end`, `turn_start`, `turn_end`, `before_subagent_spawn`, `tool_call`, `tool_result`, `assistant_message`, `session_stop`. Each event appends the payload (strings truncated to 300 characters, credential-shaped keys such as `credentialId` replaced by `[redacted]`, arrays cut at 20 items) plus `ctx.agent`, `ctx.mode` and the candidate digest to `captures/<session_id>.events.jsonl`, then applies the policy. The candidate digest is the first 16 hex characters of SHA-256 over `candidate.txt`.
- Placement confirmed: `<cwd>/.omp/hooks/pre/*.ts` is discovered and loaded as an extension; a default-exported factory receiving `pi` and calling `pi.on(name, async (event, ctx) => result)` works. **No approval step**: the module loaded and ran on the first headless run with no prompt or trust dialog (`ctx.isProjectTrusted()` is documented as always true).
- Every session ran through Terminal Commander `run_and_watch` (argv form, `wait_until: exit`, resumed with `bucket_wait` when over 60 s) as `omp.exe -p --model openrouter/z-ai/glm-5.3-flash --config <fixture>/omp-config.yml --session-dir C:\temp\omp-t3\sessions --no-title --no-context-files --no-prewalk --max-time 5m|8m --max-cost 0.5 "<prompt>"` (T8 and T9B also `--no-tools`), cwd = the fixture, environment `OMP_T3_TEST=<test>`, `OMP_T3_FIXTURE=<fixture>`, `OMP_MCP_TIMEOUT_MS=10000`, and `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_SUBAGENT_MODEL` set empty. Chair and workers: `openrouter/z-ai/glm-5.3-flash` (the cheapest role already configured; workers resolved to it through agent frontmatter or the `task` role). The OpenRouter credential was already configured in the user's OMP auth store; no key was requested, read or printed. Approval mode: the default (`yolo`), so tools ran without prompts.
- On this machine `task` runs asynchronously unless the agent sets `blocking: true`: the `task` result is only `Spawned agent <id>`, and the worker's output reaches the chair in the result of a separate `wait` tool (or by `read agent://<id>`). With `blocking: true` the `task` result carries the output inline. The hook reads worker output from either.
- All 13 `omp -p` runs exited 0 (`outcome_trust: observed`).

Known flaw in the throwaway handler, left as evidence: the completion matcher is a word match with crude negation exclusion. It cannot tell a hedged claim ("Task done in the sense that …", T2) from a plain one, and it stopped seeing a claim once the hook itself had rewritten the text (T8). The hook also releases after one refusal by default, so T5 and T6 ended with a completion claim standing while the gate state was `verifying`; that is the fixture's limit, not the harness's (T9B shows the harness keeps honouring refusals).

## Reading for an OMP adapter

- The adapter is an extension module: a TS file in `.omp/hooks/pre/` (project) or `~/.omp/agent/hooks/pre/` (user), or passed with `--extension`/`--hook`. It can call the Rust binary through `pi.exec(...)` or a child process; the process boundary is the module's choice, not the harness's.
- Hard refusal: `tool_call` (fail-closed on error) and `before_subagent_spawn`. Completion refusal: `session_stop`, main session only, not capped for explicit refusals, so the adapter must carry its own bound (the fixture used a counter) or rely on `--max-time` / `--max-cost` in headless use.
- Receipts: worker commands are observable in the worker's own session (`ctx.agent.kind === "sub"`, `parentId`), and the parent's `task` result `details.results[]` carries `id`, `agent`, `exitCode`, `output`, `usage` with cost. For async workers the delivery point is the `wait` result; the chair can also read `agent://<id>`, so the adapter should treat the worker's observed commands, not the delivered text, as evidence.
- Candidate changes are visible at `tool_call`/`tool_result` for `write` (and `edit`, `bash`, not exercised); the adapter can mark receipts stale at write time.
- The chair read the hook source, the policy and the gate state file in T2 and T9 because they live in the project tree. Gate state and policy belong outside the project, and `tool_call` should refuse writes to them, as the Claude Code adapter already does.

## Limits

- Print mode only. Interactive TUI behaviour (streamed text not retracted by `assistant_message`, operator interrupt of a refused stop, UI prompts) was not run.
- Not tested: `tool_call` refusal inside a subagent session; handler timeout behaviour; `tool_result` `isError` patching; the `edit` and `bash` write paths; `--mode json`; RPC/ACP modes.
- One cheap chair model (`glm-5.3-flash`) and one repetition per test; chair behaviour after a refusal varied (withdrew in T3 and T9, repeated the claim in T6 and T9B, re-verified in T5). Do not read chair compliance as a harness property.
- Unknown: whether `~/.omp/agent/AGENTS.md` and `RULES.md` reached the prompt despite `--no-context-files` (the session file does not store the system prompt; captures keep only its first 300 characters).

## Side effects and cost

- Sessions were written to `C:\temp\omp-t3\sessions\` via `--session-dir` (18 files, 13 main runs plus worker artefacts), not to `~/.omp/agent/sessions/`; that folder was deleted after the results were extracted. OMP itself still wrote under the home folder during the runs: 13 marker files in `~/.omp/agent/custom-session-files/` (breadcrumbs pointing at the deleted temp sessions; `omp gc --stale` prunes them), 14 log files in `~/.omp/logs/`, `~/.omp/run/daemons/*`, and updates to `agent.db`, `models.db`, `history.db`, `skill-descriptions.db` and two caches under `~/.omp/cache/`. None of these were written by this investigation directly.
- The user-level MCP servers configured for OMP were started in every run. The SymForge server created `fixtures/omp-enforcement/.symforge/index.bin` (deleted; `.symforge/` added to the fixture's `.gitignore`). In T9 and T9B the chair called Terminal Commander and two read-only memory-server operations.
- Reported cost: about 0.13 USD in total across the 13 runs and their workers, summed from the `usage.cost.total` of every captured `assistant_message` (main and worker sessions). Largest: T2 0.030, T9B 0.029, T9 0.024, T5 0.021.
- `candidate.txt` was restored to `candidate v1`. Captures total about 0.8 MB; one capture (T9B) had the memory-server content replaced with `[redacted for commit: user memory-server content]`. The fixture `.gitignore` excludes `captures/*.log` and `.symforge/`.

## Blocked by the no-home-changes rule

- **Isolating the runs from user-level MCP servers.** Needed change: add the server names to `disabledServers` in `~/.omp/agent/mcp.json`, or create a dedicated profile (`omp --profile <name>`, which creates `~/.omp/profiles/<name>/` and needs its own provider login). Why: in print mode OMP starts every configured server, the chair used them (T9, T9B), and one wrote an index into the fixture. Not done; the effect is recorded above.
- **Keeping OMP's own state writes out of the home folder.** Needed change: point `PI_CODING_AGENT_DIR` at a directory outside home, which would require copying the provider credentials there. Why: logs, databases, caches and session markers are written under `~/.omp` on every run. Not done; credentials were not touched.
- Nothing under `~/.omp`, `~/.agents`, `~/.claude` or the Jev engine was edited by this investigation; the user's OMP config and context files were only read (config with credential-shaped lines filtered out).
