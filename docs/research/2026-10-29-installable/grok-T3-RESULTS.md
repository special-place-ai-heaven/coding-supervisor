## Adapter mode this evidence supports (one line)

**Enforcing on three named paths, advisory/audit everywhere else, for harness mechanics only (measured with a scripted model, not yet with a live xAI model):** enforcing at (1) `PreToolUse` denial of a tool call (an explicit `deny` blocks; a timeout, crash or malformed reply fails open), (2) `Stop` refusal of a turn-ending completion claim, bounded by an 8-continuation cap per turn, and (3) `SubagentStop` refusal of a worker's handback, same bound; advisory/audit at `PostToolUse` annotation of a foreground worker result, at background worker results (seen only by `SubagentStop` in the worker's session and as a wake-up prompt), and at the acceptance moment itself, for which no event exists.

The public web page (https://docs.x.ai/build/features/hooks.md, read 2026-10-29) still says `PreToolUse` is "the only blocking event" and that stdout of every other event is ignored. On 1.0.60 that is wrong: the bundled user guide (`~/.grok/docs/user-guide/10-hooks.md`, shipped with this binary) documents `Stop`/`SubagentStop` blocking and `PostToolUse` annotation and replacement, and the captures below show them working. The survey's prior ("Stop and SubagentStop only observe", `SURVEY.md` footnote 25 and the Grok paragraph) is superseded for 1.0.60.

## Limits

- Everything here is harness behaviour under a scripted model. A live chair might ignore `Stop hook feedback`, and then the bound is the 8-continuation cap; that cooperation is unmeasured for Grok.
- Every refusal path fails open on a hook timeout, crash or malformed reply. Only `PreToolUse` timeout was exercised.
- Hook timeout defaults: 5 s for `PreToolUse` and the passive events; 600 s for `Stop`, `SubagentStop`, `PostToolUse` (bundled guide). The `timeout` field is honored (point 1b).
- The handler's receipt logic is throwaway: a single fixture-level receipt file, cleared between runs by the operator, and keyed on the literal `echo check-ok`. A real adapter must link worker sessions to the chair through `SubagentStart.subagentId`.
- Not tested: `PostToolUse` `updatedToolOutput`, `continue:false`, `UserPromptSubmit` blocking, `get_command_or_subagent_output` as the background delivery path, exit-code-2 replies on `Stop`, and the HTTP hook type.
- The web documentation and the bundled guide disagree; the bundled guide matched every behaviour tested here.

## Blocked by the no-home-changes rule

1. **Live xAI model sessions.** `grok models` and `grok -p` report `Not signed in`; `~/.grok/auth.json` does not exist and `XAI_API_KEY` is not set. Needed: the owner signs in. Options: (a) `grok login` against the real home, which writes `~/.grok/auth.json`, a home change; (b) `GROK_HOME=C:\temp\grok-t3\home grok login --device-code` with the owner approving the code in a browser, which keeps the credential out of the real home; (c) an `XAI_API_KEY` in the environment of the run only. Then rerun `run-scenario.sh` with `-m grok-4.5` (the cheaper of the two listed models is not stated; both are listed) and the `[model.fake-chair]` table removed, prompting the chair in plain language instead of the `SCENARIO:` markers, to measure whether a live chair heeds `Stop hook feedback`.
2. **`--trust` against the real home.** It writes `~/.grok/trusted_folders.toml` and trusts the whole repository root. Done instead against the temp home. A live run with credentials in the real home can use `GROK_FOLDER_TRUST=0` per invocation, but it would then also need `HOME` relocated to keep the user's Claude Code hooks from running, because `GROK_CLAUDE_HOOKS_ENABLED=false` did not remove them from `grok inspect`.
