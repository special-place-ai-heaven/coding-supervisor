# Harness locations: where five coding agents read skills, instructions, MCP servers and hooks

As of 2026-10-29. Every page below was read on 2026-10-29 (crawl4ai REST for web pages, `gh api` / raw GitHub for the OMP docs and release lists). Where a claim could not be confirmed it says UNCONFIRMED. Nothing is filled from memory. Confidence: high = stated in an official page I read; medium = an official page implies it, or only a secondary source; low = inferred.

Local state on this machine (read-only checks, 2026-10-29): `claude`, `codex`, `cursor-agent`, `omp` and `grok` are all installed (versions in each section). One trap: the bare command `agent` (the name Cursor's docs use) does not start Cursor here. `where agent` lists `C:\Users\rakovnik\AppData\Roaming\npm\agent.exe` and `C:\Users\rakovnik\.grok\bin\agent.exe` before `C:\Users\rakovnik\AppData\Local\cursor-agent\agent.cmd`, and `agent --version` run through PowerShell printed `grok 0.1.210 (8b63e9068)`. Use `cursor-agent` for Cursor on this machine.

Design note that falls out of the research: the Agent Skills user directory `~/.agents/skills` is read by Codex (documented), Cursor (documented) and Grok (documented). Claude Code does not document it, and OMP reads it through its `agents` provider. So `~/.claude/skills` is still required for Claude Code, and `~/.omp/agent/skills` is the safe OMP-native directory.

## Gaps

- G1. Grok release dates and the latest version come from secondary trackers (Releasebot, Havoptic) because https://x.ai/build/changelog returned HTTP 403 to crawl4ai and WebFetch. No official page stating the current Grok Build release was readable.
- G2. Codex docs list `$HOME/.agents/skills` and `/etc/codex/skills`, not `~/.codex/skills`. Cursor and OMP docs say they read `~/.codex/skills` for compatibility, and the folder exists locally, but no Codex page I read says Codex scans it. The `codex --version` flag is not described in the CLI reference text I read; it works locally.
- G3. Codex project trust: the config key is documented (`projects.<path>.trust_level`); the interactive trust dialog was not read. The Windows path spelling inside that key follows what this machine config uses (`[projects.'E:\project']`); it is not a documented rule.
- G4. Cursor: (a) the MCP approval step is documented only through `agent mcp enable` and `--approve-mcps`; it is not stated whether it applies to project-scoped servers only, or what a `-p` run does without `--approve-mcps`. (b) `CURSOR_CONFIG_DIR` is documented only for `cli-config.json`; whether `~/.cursor/skills`, `mcp.json` and `hooks.json` follow it is not stated, so a Cursor fixture run probably needs a separate `USERPROFILE` (UNCONFIRMED). (c) Cursor docs call the command `agent`, which is shadowed on this machine. (d) The hooks page is the shared editor + CLI page; CLI hook support rests on the CLI changelog entries. (e) The headless page contradicts itself on whether `-p` writes files without `--force`; verify live before relying on either.
- G5. Grok: `--trust` is named on the hooks page but is absent from the CLI reference flag table; project-level `.agents/skills` is not documented; the role of `description` in automatic skill loading is implied rather than stated; Stop and SubagentStop cannot block (documented), so completion cannot be refused through Grok hooks alone. A second `agent.exe` that reports `grok 0.1.210` is on PATH and was not investigated.
- G6. OMP: the docs live in the repository, not on an omp.sh site I could read. The full merge order of context files across providers was not read to the end; no blocking subagent-completion event was found (only `before_subagent_spawn`, and `session_stop` explicitly never fires for subagents); whether `~/.agents/skills` loads without an `enabledProviders` opt-in for the `agents` provider is not clear from the page; OMP hooks are code modules, so an install cannot ship a declarative hook file for it.
- G7. Claude Code: the hand-written JSON shape of user-scope servers inside `~/.claude.json` is not shown, so the install should use `claude mcp add --scope user`. There is no `--cwd` flag in the CLI reference. Under `-p`, project `.mcp.json` servers and settings-file hooks load without any trust prompt unless `--bare` is used, which matters for a fixture project.
- G8. Windows: the supervisor binary must resolve as `supervisor` on `PATH` (`supervisor.exe`), or each file must carry an absolute path; none of the five docs promises `.cmd` / `.bat` resolution for stdio MCP commands on Windows. Not tested here.
- G9. Not read, outside scope: enterprise and managed layers for each harness (managed settings, `requirements.toml`, MDM) that can override or disable all of the above.
